# File upload and retrieval web application

## Context

People often need a simple way to move screenshots and small diagnostic files from a phone or workstation into a location where they can be reviewed later. Existing file-transfer tools can be unnecessarily broad, difficult to access from a mobile browser, or lack useful retention and archive semantics.

This project provides a focused upload and retrieval service. It should remain useful across different hosting environments rather than encoding one operator's internal hostnames, networks, reverse-proxy names, automation systems, or infrastructure layout.

## Goal

Provide a simple mobile-friendly web application that accepts an upload, asks for a descriptive name suffix, stores a timestamped file, and provides links and filtered listings for later retrieval.

## Settled decisions

1. The application is a general-purpose self-hosted utility, not a deployment-specific integration.
2. The initial interface is a web application; no MCP server is included in the first release.
3. Retention is configurable and defaults to 60 days.
4. A user can mark a file as archived; archived files are retained indefinitely.
5. Initial supported file classes are images, `.log`, `.txt`, and `.html` files.
6. Container deployment is optional. An example Compose configuration may be documented for users who want it, but the application must not require Compose.

## Scope

- Mobile-friendly upload page.
- Upload flow that accepts a file and a descriptive suffix.
- Timestamped generated filenames that preserve the safe original extension.
- File metadata and a stable download/share link.
- Listing views for all files, today, this week, and this month.
- Search/filter by generated filename or descriptive suffix.
- Archive/unarchive action.
- Configurable retention cleanup with archived files excluded.
- Persistent application metadata and file storage.
- Health endpoint suitable for deployment monitoring.
- Documentation for local development and operation.
- Optional example deployment configuration, kept separate from the core application contract.

## Functional requirements

### Uploads

- The upload form must work from a current mobile browser.
- The user must provide a non-empty descriptive suffix.
- The generated filename must contain a local timestamp and a sanitised suffix, for example `2026-09-19-10-46-12-router-status.png`.
- The original extension must be retained only after validation against the supported file class.
- The application must reject path traversal, executable extensions, unsupported types, and uploads over the configured size limit.
- The application must validate content type from file content where practical, not trust the browser-provided MIME type alone.
- The application must never use an untrusted original filename as a filesystem path.

### Listings and retrieval

- All listings must show filename, size, upload time, archived state, and a download/share link.
- The application must provide today, current-week, and current-month filters using the configured application timezone.
- Download responses must use the stored generated filename and correct content type.
- Image files may be shown with thumbnails or previews; text and HTML files must not be rendered inline in a way that permits stored content to execute in the application origin.
- The listing must remain usable when no files match a filter.

### Retention and archive

- `RETENTION_DAYS` must be configurable and default to `60`.
- A scheduled cleanup mechanism must delete only non-archived files older than the retention period.
- Archived files must not be removed by retention cleanup.
- The archive state must be stored durably with file metadata.
- Cleanup must be idempotent and must not delete a file when metadata and filesystem state disagree without a safe, explicit rule.

## Deployment and portability requirements

- The core application must be runnable without a particular reverse proxy, internal DNS name, orchestration system, or host directory layout.
- Persistent storage locations and runtime settings must be configurable through documented environment variables or equivalent configuration.
- No uploaded files, generated database, local environment files, or secrets may be committed to the public repository.
- An optional Compose example may show one way to run the application with persistent storage. It must be clearly labelled as an example and must not be presented as the only supported deployment method.
- Deployment examples must use generic placeholders and must not include private hostnames, internal infrastructure names, or operator-specific paths.
- Retrieval by another application or agent may be documented as a generic API or read-only storage integration, but it is not required for the first release.

## Non-goals

- MCP integration.
- Public internet access as a hosting requirement.
- Multi-user accounts or per-file sharing permissions.
- Cloud object storage.
- Automatic OCR, image analysis, or content classification.
- Editing uploaded files in the browser.
- Indefinite retention for unarchived files.
- Requiring a particular container runtime or reverse-proxy product.

## Acceptance criteria

- A user can upload a supported image, log, text, or HTML file from a current mobile browser.
- The upload requires a suffix and produces a timestamped generated filename.
- The newly uploaded file appears in the all-files and appropriate period listing.
- The download/share link retrieves the exact stored file.
- Today, week, and month filters return correct results for the configured timezone.
- A file can be archived and remains present after retention cleanup.
- An unarchived file older than the configured retention period is eligible for cleanup.
- Unsupported files, unsafe names, and oversized files are rejected without creating orphaned metadata.
- The application and storage survive application restart and deployment recreation where supported by the chosen deployment method.
- Application tests and static validation pass.
- Any optional deployment example is generic, documented, and independently validated.

## Implementation notes

The implementation may use a small Python web service with SQLite metadata and a configurable file directory. The storage design must separate the metadata database from the file payload directory so read-only integrations cannot accidentally expose mutable application state.

Generated names should be unique even when two uploads occur within the same timestamp unit. A stable opaque file ID should be used for application routes; the generated filename is display and download metadata, not an authorization boundary.

The application should expose a health endpoint and keep cleanup separate from request handling. The first implementation should prefer a simple scheduled command or deployment-supported maintenance path over embedding an unbounded background scheduler in the web process.

## Risks and mitigations

- **Public repository:** keep all deployment secrets and local uploaded data outside Git.
- **Unauthenticated deployment:** document that access control is supplied by the chosen deployment environment and is not implicitly provided by the first application release.
- **Stored HTML:** prevent stored HTML from executing in the application origin; serve it as a download or with a safe content-disposition policy.
- **Disk growth:** configure retention, expose cleanup status, and allow indefinite retention only through explicit archive marking.
- **Metadata/file divergence:** use atomic writes and explicit reconciliation rules.
- **Mobile usability:** test upload and listing flows at phone-sized viewport widths.

## Validation

From the repository root, after implementation:

```bash
uv run pytest
# or the repository's documented isolated test command

git diff --check
```

If an optional Compose example is added, validate it separately with the relevant static Compose configuration command. Deployment validation, performed only with separate authorization, must verify upload, listing, download, archive, cleanup, and persistence behaviour in the selected deployment environment.

## Lifecycle

This specification is proposed for review. Implementation and deployment changes are not authorized by this specification alone.
